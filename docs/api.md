# API

## Overview

The server exposes a REST API that allows recording nodes to upload detections and operational status.

The API is designed for communication between recording nodes and the central server. It is not intended to be a general-purpose public API.

All requests are sent over HTTPS and use JSON request bodies.

---

# Authentication

Requests must include a bearer token in the `Authorization` header.

```
Authorization: Bearer <INGESTION_API_TOKEN>
```

Requests without a valid token receive:

```
HTTP 401 Unauthorized
```

> **Note**
>
> The current implementation uses a shared ingestion token. Future versions will support per-node authentication.

---

# Endpoints

The API currently exposes two ingestion endpoints.

| Endpoint | Purpose |
|----------|---------|
| `POST /detections/` | Upload BirdNET detections |
| `POST /heartbeat/` | Upload node health information |

---

# Detection Upload

```
POST /detections/
```

Uploads one or more BirdNET detections generated by a recording node.

Each request contains:

- Station metadata
- One or more detections

Typical workflow:

```
  Record Audio
        │
        ▼
     BirdNET
        │
        ▼
Detection Metadata
        │
        ▼
POST /detections/
```

The server validates the request, stores the detections in PostgreSQL, and associates them with the appropriate recording station.

---

## Successful Response

```
HTTP 200 OK
```

Example response:

```json
{
    "status": "ok",
    "inserted": 8
}
```

---

# Heartbeat Upload

```
POST /heartbeat/
```

Uploads operational information about a recording node.

Heartbeat uploads are independent of BirdNET detections.

A node should continue sending heartbeats even when no birds are detected.

Heartbeat information includes metrics such as:

- Timestamp
- Uptime
- Available memory
- Available disk space
- CPU temperature (if available)
- Wi-Fi signal strength (if available)
- Software version

---

## Successful Response

```
HTTP 200 OK
```

Example response:

```json
{
    "status": "ok"
}
```

---

# Error Responses

| Status | Description |
|---------|-------------|
| `200 OK` | Request accepted |
| `400 Bad Request` | Invalid request body |
| `401 Unauthorized` | Missing or invalid authentication |
| `404 Not Found` | Endpoint does not exist |
| `422 Unprocessable Entity` | Request validation failed |
| `500 Internal Server Error` | Unexpected server error |

---

# Data Validation

FastAPI validates all incoming requests using Pydantic models.

Invalid payloads are rejected before any database operations occur.

Validation includes:

- Required fields
- Data types
- Timestamp parsing
- Nested object validation

---

# API Documentation

When the server is running, FastAPI automatically generates interactive API documentation.

Swagger UI:

```
http://<server>:8000/docs
```

OpenAPI schema:

```
http://<server>:8000/openapi.json
```

These endpoints provide complete request and response schemas generated directly from the application source code.

---

# Versioning

The API is currently unversioned.

Breaking API changes should be introduced cautiously to maintain compatibility with deployed recording nodes.

Future releases may introduce explicit API versioning if required.

---

# Design Principles

The API was designed around several principles.

- Lightweight requests
- JSON-based communication
- Stateless endpoints
- Server-side validation
- Metadata only (no audio uploads)
- Independent heartbeat monitoring

Keeping the API small simplifies deployments and allows recording nodes to remain lightweight and resilient.
